# bespoke 페이지 작업 기록

`pages/bespoke/` 폴더의 작업 내역입니다. 저장소 전체 기록은 `docs/PROJECT_CONTEXT.md`에
있고, 이 문서는 이 폴더 안에서만 끝나는 작업을 남깁니다.

이 폴더에는 **페이지 세 개**가 들어 있습니다.

| 파일 | 화면 | CSS |
|---|---|---|
| `index.html` | Bespoke 메인 | `css/bespoke.css` (+ `bespoke_base.css`) |
| `reservation.html` | 예약 폼 | `css/reservation.css` (+ `bespoke_base.css`) |
| `reservation_done.html` | 예약 완료 | `css/reservation_done.css` (+ `bespoke_base.css`) |

**`css/bespoke.css`와 `js/bespoke.js`는 `index.html`만 불러옵니다.** 이 두 파일을
고쳐도 예약 페이지 두 개에는 영향이 없습니다. 반대로 `css/bespoke_base.css`는
세 페이지가 함께 쓰므로 고칠 때 세 페이지를 모두 확인해야 합니다.

## Process 섹션 — 스크롤 단계 전환 (2026-08-09)

단계가 화면 가운데를 지날 때마다 툭툭 바뀌던 것을, **섹션을 붙잡아 두고 한 단계씩
머물면서 넘어가는** 방식으로 바꿨습니다.

수정 파일은 두 개뿐입니다. **HTML은 건드리지 않았습니다.**

- `css/bespoke.css` — process 블록에 상태 규칙 추가 (1071 → 1153줄)
- `js/bespoke.js` — process 블록 전체 교체, `initProcessMotion()` 추가

### 레퍼런스 — thecube.dk Services

실제로 열어 구조를 실측했습니다.

| 항목 | 실측 |
|---|---|
| 항목 하나(`.serv-item`) | 1440px = 화면(720) 2장 |
| 안쪽 콘텐츠(`.ser-item-content`) | `position: sticky; top: 0`, 720px |
| 미디어(`.service-sticky`) | 섹션 전체 길이에 걸친 sticky **한 장** |
| transform / opacity 애니메이션 | **없음** — 순수 CSS sticky 스택 |

핵심은 **"한쪽에 붙어 있는 미디어 + 차례로 자리를 넘겨받는 텍스트"**입니다.
이 process 섹션이 이미 같은 구성(왼쪽 5단계 목록 + 오른쪽 sticky 이미지)이라
코드를 옮기지 않고 넘어가는 방식만 다시 만들었습니다.

### ★ 레퍼런스 구조를 그대로 쓸 수 없었던 이유

항목마다 화면 하나씩 주려면 5단계를 세로로 흩어야 하는데, **이 시안은 목록 5개가
한 화면에 다 보이는 구성입니다**(1840+에서 5×160 + 4×40 = 960px, 이미지 높이와 동일).
흩는 순간 Figma 정렬이 무너집니다.

그래서 **섹션을 화면 가운데에 붙잡고(GSAP pin) 그 안에서 진행도를 5구간으로
나눴습니다.** 보이는 그림은 시안 그대로이고, 한 단계씩 머무는 시간만 생깁니다.

1504px 섹션을 1080px 화면에 `start: "center center"`로 pin하면 잘리는 것은
**위아래 padding 272px뿐**입니다 — 목록(top 60 / bottom 1020)과 이미지는 온전히
들어갑니다. 이것이 pin을 쓸 수 있었던 전제입니다.

### 화면 조건에 따라 세 갈래

| 조건 | 방식 | 스크롤 |
|---|---|---|
| ≥1280px **및** 높이 ≥1060px | **A. pin + scrub** | 화면 3.6장(1080 기준 3888px) |
| ≥1280px, 높이 ≤1059px | **B. pin 없는 scrub** | 섹션 자체 길이 |
| 그 외(모바일·태블릿·모션 감소·GSAP 없음) | **C. IntersectionObserver** | 가로채기 없음 |

**★ 폭만이 아니라 화면 높이 조건이 필요합니다.** 1280px 폭에서 목록이 995px인데
900px 화면에 pin하면 05번이 잘립니다(실측). 낮은 화면은 B로 내려갑니다.
1060px이면 1840+ 레이아웃(960px)도 1280~1839 레이아웃(995px)도 여유 있게 들어갑니다.

### 전환 값

- **이미지 크로스페이드** — 이웃한 두 장의 불투명도 합이 **항상 정확히 1**입니다.
  `smoothstep(t) + smoothstep(1-t) === 1`이라는 성질을 씁니다. 중간에 어두워지는
  구간이 없습니다. 들어오는 사진은 `scale 1.06 → 1`로 내려앉습니다
  (`.process_image`의 `overflow: hidden` 안이라 레이아웃 영향 없음).
- **활성 강조** — 불투명도 0.4 → 1, 비활성 단계는 8px 안쪽으로 물러남(transform만),
  번호가 딥그린(`--color_point`)으로.
- **진행 표시** — 시안에 없는 장식을 새로 얹는 대신 **원래 있던 각 단계의
  `border-bottom`에 딱 겹쳐** 딥그린 선이 왼쪽부터 그어집니다. 지나온 단계는
  채워진 채로 남고, 끝에 닿으면 다섯 줄이 모두 그어집니다.
- 색만으로 상태를 알리지 않습니다 — 불투명도·들여쓰기·진행선이 함께 바뀝니다.

### 반드시 지켜야 하는 것

1. **`.is_scrub_ready`가 붙으면 transition을 꺼야 합니다.** A·B는 매 프레임 인라인
   값을 덮어쓰는데 transition이 남아 있으면 값이 뒤늦게 따라와 뭉개집니다.
   자식 요소(`.process_step_num`의 color)는 transition이 상속되지 않으므로
   그대로 살아 있습니다 — 숫자 색만 부드럽게 바뀝니다.
2. **인라인 스타일을 손으로 지워야 합니다.** GSAP은 자기가 만든 트윈만 되돌립니다.
   `onUpdate` 안에서 부른 값 쓰기는 `gsap.context`에 기록되지 않으므로,
   matchMedia 정리 함수에서 `clearProcessInlineStyles()`를 직접 부릅니다.
   **이걸 빼면 조건이 바뀐 뒤에도 A·B의 마지막 상태가 굳어 남습니다.**
3. **진행선 값은 CSS 변수(`--process_step_fill`)로 넘깁니다.** 의사요소에는
   인라인 스타일을 줄 수 없기 때문입니다. C 경로에서는 `.is_active` /
   `.is_passed` class가 같은 변수를 1로 세웁니다 — 인라인이 없으면 class가,
   있으면 인라인이 이깁니다.
4. **`::after`의 `bottom`은 `-1px`입니다.** 절대배치의 기준은 padding box라
   `bottom: 0`이면 기존 border 바로 위에 놓입니다. `-1px`이어야 딱 겹칩니다.
5. **사진 짝짓기는 순서가 아니라 `process_image_<data-step>` 이름입니다.**
   마크업 순서가 바뀌어도 어긋나지 않습니다.

### 조절값

`js/bespoke.js`의 process 블록 상단에 모여 있습니다.

| 상수 | 현재 | 의미 |
|---|---|---|
| `PROCESS_STEP_SCROLL` | 0.72 | 단계 하나에 배정하는 스크롤(화면 높이 배수) |
| `PROCESS_SCRUB` | 0.6 | 스크롤을 따라오는 지연(초). 전환의 여운 |
| `PROCESS_INACTIVE_OPACITY` | 0.4 | 비활성 단계 불투명도 |
| `PROCESS_INACTIVE_SHIFT` | 8 | 비활성 단계가 물러나는 거리(px) |
| `PROCESS_IMAGE_SCALE` | 1.06 | 들어오는 사진의 시작 배율 |

**뒤 세 개는 `bespoke.css`의 기본값과 같아야 합니다.** C 경로가 CSS 값을 쓰기
때문에, 한쪽만 바꾸면 A·B와 C의 모습이 달라집니다.

### ★ 확인하지 못한 부분

- **미리보기 패널이 process 섹션을 합성하지 못했습니다.** 히어로는 캡처되는데
  그 구간은 크림색 빈 화면만 나옵니다(pin을 꺼도 동일). 위 수치는 전부
  `getBoundingClientRect` / `getComputedStyle` 측정입니다.
  **흐르는 모습, 단계당 머무는 시간, 여운의 체감은 사용자가 직접 봐야 합니다.**
- 미리보기 탭이 `document.hidden`이라 **class 변경 후의 다시 칠하기(번호 딥그린)를
  눈으로 보지 못했습니다.** DOM 상태와 선택자 매칭(3개 일치)으로만 확인했습니다.
- **이 브라우저는 `resize`와 `matchMedia change`를 전혀 발생시키지 않습니다**
  (프로브를 걸고 1080→900으로 바꿔 확인 — 0건). 해제 검증은
  `gsap.matchMediaRefresh()`로 직접 재평가시킨 결과입니다.
  **실제 창을 마우스로 끌어 줄여 보는 확인은 사용자가 해야 합니다.**
- **IntersectionObserver가 이 환경에서 한 번도 발화하지 않습니다**(새 옵저버를
  따로 만들어 확인 — 콜백 0건). C 경로의 실제 단계 전환은 확인이 필요합니다.
  다만 이 경로는 **기존 코드와 같은 방식**이라 이번 변경으로 달라진 것은 없습니다.
- `prefers-reduced-motion: reduce` 실제 동작. 이 환경에서 에뮬레이트할 수
  없었습니다(philosophy·atelier와 동일한 `gsap.matchMedia()` 게이트로 작성).

## 이 폴더의 남은 문제

`docs/PROJECT_CONTEXT.md`의 "Bespoke 다음 작업"과 같은 내용입니다.

1. **메인 히어로 영상** — `index.html:41`이 `assets/main/bespoke_main.mp4`를
   가리키는데 파일이 없습니다(404). 저장소에 시안의 히어로 장면과 맞는 영상이
   없습니다.
2. **헤더가 시안보다 30px 낮습니다**(66 vs 96). `common/css/layout.css`의 공통
   컴포넌트라 다른 페이지가 같이 바뀝니다.
3. 예약 폼 달력의 이전·다음 달 버튼이 아직 동작하지 않습니다(2026년 8월 정적 마크업).
4. `.begin_card`의 "View Guide" / "View Process" 버튼과 "Contact" 링크가
   `href="#"` 상태입니다.
